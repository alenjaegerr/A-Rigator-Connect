# A-Rigator MQTT Command Protocol

Status: implementation contract for the ESP32 firmware and A-Rigator Connect app.

## Topics

All topics are scoped to one provisioned robot:

- `arigator/v1/{robotId}/command` — app to robot, QoS 1, non-retained
- `arigator/v1/{robotId}/ack` — robot to app, QoS 1, non-retained
- `arigator/v1/{robotId}/telemetry` — robot to app, QoS 0, non-retained
- `arigator/v1/{robotId}/availability` — robot availability, QoS 1, retained

The broker ACL must restrict each robot credential to its own topic prefix. TLS certificate validation is mandatory. Never ship broker administrator credentials in the mobile app or firmware source.

## Command envelope

Publish one JSON object per command:

```json
{
  "version": 1,
  "commandId": "client-generated-uuid",
  "robotId": "registered-robot-id",
  "command": "forward",
  "issuedAt": 1794900000,
  "ttlMs": 1500,
  "payload": {}
}
```

- `version`: protocol version; currently `1`.
- `commandId`: unique UUID generated by the app for each attempt. Retries must reuse the same ID.
- `robotId`: must match the ID in the subscribed topic and the robot's provisioned configuration.
- `command`: one of the names in the command list below.
- `issuedAt`: Unix time in seconds (UTC).
- `ttlMs`: command lifetime. Firmware must reject expired commands. Movement and heartbeat commands should use a short lifetime (1500 ms); stop commands may use a longer lifetime (5000 ms).
- `payload`: command-specific object; use an empty object when no arguments are required.

The firmware must reject malformed JSON, unsupported versions, mismatched robot IDs, unknown command names, missing IDs, invalid timestamps, expired commands, and oversized payloads. Do not execute a command directly in the MQTT callback.

## Acknowledgement envelope

Publish an acknowledgement for every command that reaches the main-loop dispatcher:

```json
{
  "version": 1,
  "commandId": "same-client-generated-uuid",
  "robotId": "registered-robot-id",
  "status": "executed",
  "code": "OK",
  "message": "Command executed",
  "timestamp": 1794900001
}
```

Statuses:

- `executed`: command passed validation and the requested action was applied.
- `rejected`: command was understood but refused by robot state or safety interlocks.
- `expired`: command TTL elapsed before execution.
- `duplicate`: this command ID was already processed; do not execute it again.

The app correlates acknowledgements by `commandId`. A QoS 1 delivery or app retry must never cause a physical action to run twice. Keep a bounded recent-ID cache on the ESP32. A command that cannot be queued should not be silently replaced by a newer command.

## Irrigation profile payload

```json
{
  "leftSeconds": 3,
  "backSeconds": 3,
  "rightSeconds": 3,
  "repeatCount": 1
}
```

Match the existing firmware validation: each duration is 0–60 seconds, repeat count is 1–20, and at least one direction duration must be greater than zero.

## Current firmware implementation

The ESP32 dispatcher currently enables only `stop`, `forward`, `reverse`, `pump_on`, `pump_off`, and `heartbeat`. Other listed commands are protocol targets and must be rejected until their shared safety-aware execution paths are implemented. The firmware now requires the **ArduinoJson** library by Benoit Blanchon in addition to PubSubClient.

## Safety and execution rules

1. MQTT callback only copies bounded payloads into the command queue. Parse, validate, deduplicate, and execute from the main loop.
2. The ESP32 remains the final authority. Reuse the same safety checks as local HTTP: emergency-stop latch, current operating mode, obstacle interlocks, pump interlocks, and control leases.
3. Reject stale movement commands. A delayed `forward` must never run after its TTL.
4. A command acknowledgement means the robot accepted/applied the command, not that a long-running irrigation or autonomous task has completed. Task completion belongs in telemetry/state.
5. Keep local AP/HTTP control available if the router or broker is offline. MQTT failure must not disable local operation.
6. Publish telemetry periodically at a modest rate and on important state changes. Availability uses the retained last-will message.
7. Never put credentials, passwords, or CA private keys in command payloads, telemetry, logs, or acknowledgements.
